# 猫卷 · AI 语音问答能力可行性评估

> 评估日期：2026-09-14　｜　评估方式：三路独立调研（移动端音视频工程 / LLM 应用架构与成本 / 产品与用户研究），结论交叉核对后汇总
> 需求原始表述：*「期末周复习时时不时进行专业名词的提问，要求不能限制功能使用时间」*，形式上做成「AI 在线语音通话」

---

## 一、结论先行

**1. 值得做，但不要做成「通话」。** 用户设想的使用场景（期末周、图书馆/自习室复习中随手问名词）恰恰是**最不适合开口说话**的场合。产品侧建议做成：**按住说话 → 转写可编辑 → 默认文字回答 → 需要时一键朗读**。这是一次交互形态的修正，不是砍功能。

**2.「不能限制使用时间」是伪需求，不需要靠「通话」来实现。** 本 App 是 BYOK（用户自己的 Key，费用自付），产品侧本来就没有、也不该有时长限制。真正的限制来自**用户自己 Key 的余额**和**模型厂商的单会话硬上限**，这两条都与「做成通话」无关。

**3. 若坚持做「通话」形态，技术上可行，但要接受两道硬约束**：
- **成本档位**：只有 flash/轻量档的端到端实时模型能把成本压到约 ¥10/小时以内（阿里 qwen3.5-omni-flash-realtime、智谱 GLM-Realtime-Flash）；OpenAI 的 realtime 档在期末周 7 天用完可能花 ¥100–360，且需代理 + 外卡。
- **单会话上限**：OpenAI 60 分钟、通义 120 分钟（官方文档）。「不限时」只能做到**不限累计时长**，单次到顶需要自动重连。

**4. 实现难度 4/5；最难的一环不在 AI，在 Android 实时音频链路**（低延迟采集 + 流式播放 + 后台麦克风 + 前台服务类型 + 音频焦点/路由）。管线式约 **8–15 人日**，端到端实时约 **20–35 人日**。

---

## 二、场景校准：为什么「通话」不是最优解

把「期末周问名词」拆成真实场景：

| 场景 | 姿势 | 交互要求 | 语音通话是否合适 |
|---|---|---|---|
| 图书馆 / 自习室复习中 | 手机架起或手持，戴耳机 | **不能出声**，输入要快，答案默认静默 | ✗ 最不适合——而这恰是主战场 |
| 宿舍 / 家里复习 | 手机放桌，手在写字 | 免手，可出声 | △ 按住说话已足够，不必常驻通话 |
| 通勤 / 排队 | 耳机，手机在口袋 | 免眼免手，可出声 | ✓ 通话有优势，但占比低 |
| 睡前过一遍 | 躺床关灯 | 免眼、小声、可朗读 | ✓ 通话式最贴合，但低频 |

**最大阻力不是隐私，是社交成本。** 目标用户的高频使用场景禁止出声。因此语音输入必须支持**耳语**，答案**默认文字**，朗读单独给按钮。

**竞品也都这么做**：ChatGPT 语音模式按分钟配额、静默超时会结束；多邻国 Max 的语音练习是「有边界的一次练习」；Anki 生态只有卡片发音类插件，没有通话型插件。**没有一家把「无限通话」当卖点。**

> 注：这一节是对需求前提的修正，不是否决。用户的真实诉求是「复习途中随手用语音问一句」，那个诉求成立且值得满足。

## 三、技术现状与实现难度

### 3.1 现状盘点（正式仓库实测）

| 项 | 结论 | 依据 |
|---|---|---|
| 音频依赖 | 仅 `audioplayers`（播放提示音），**无录音能力** | `pubspec.yaml` |
| `RECORD_AUDIO` 权限 | **没有** | `android/app/src/main/AndroidManifest.xml` |
| 保活能力 | 已有前台服务（`flutter_foreground_task`，类型 `specialUse`），可复用 | `lib/services/reminder_service.dart` |
| AI 层 | `http` 一次性 POST，OpenAI 兼容，BYOK | `lib/services/ai_service.dart` |
| Windows | 发布 exe，但无任何 Windows 录音插件 | — |

### 3.2 两条技术路线

| | 路线 A：端到端实时语音 | 路线 B：管线式（推荐先做） |
|---|---|---|
| 形态 | 音频进、音频出，连 Realtime API | 流式 STT → 现有 LLM → 流式 TTS |
| 首声延迟 | 约 0.5–1 s | 约 1.5–2.5 s |
| 可控性 | 差（VAD/打断/回声依赖服务端，弱网红线是整通话中断） | 好（每轮显式，失败只丢一轮，可重试） |
| 复用现有 Key | ✗ 需另开支持实时语音的服务商 | ✓ 继续用现有 DeepSeek 类 Key，只补 STT/TTS |
| Flutter 侧 | WS 长连 + PCM16 收发 + 抖动缓冲播放队列；`audioplayers` 不够用，需自写平台通道（AudioTrack）才够低延迟 | `record` 流式采集 + WS STT + 现有 AI（需补 SSE 流式解析）+ 流式 TTS 边收边播 |
| 工作量 | 20–35 人日 | **8–15 人日** |

**关键判断：路线 B 明显更适合这个项目**——它复用已有的 BYOK 文本 Key，不要求用户再开一家服务商，工程风险也低一个量级。而路线 A 需要用户**另开阿里/火山/智谱的 Key**（实时协议不在「OpenAI 兼容接口」的复用范围内），这是一个真实的使用门槛。

### 3.3 Android 平台约束（重点）

- **权限**：需新增 `RECORD_AUDIO`（运行时申请）。Android 14 起，**后台访问麦克风必须由 `microphone` 类型的前台服务支撑**，还需额外声明 `FOREGROUND_SERVICE_MICROPHONE`；现有服务类型要从 `specialUse` 扩为 `specialUse|microphone`。
- **息屏/切后台**：技术上可行，但必须在 App 可见时启动前台服务（通话入口天然满足）。现有电池优化豁免与 `WAKE_LOCK` 已具备。
- **音频焦点**：来电/导航会抢占焦点，需显式处理 transient loss（`audio_session`），通话态建议原生 `MODE_IN_COMMUNICATION`。
- **路由**：蓝牙/有线耳机切换需要原生 `AudioManager` 调用，纯 Dart 无解。
- **发布链影响**：新增权限会被「四维基线门禁」判为差异（`tools/reference_check` 目前只白名单了 3 条 Wi-Fi 权限），发版前必须评审后 `REFCHECK_MERGE=1` 并入。
- **商店合规**：麦克风需显著披露与知情同意、Data safety 声明音频上传第三方；Play Console 需申报 FGS microphone 用途。

**最难的一环：Android 实时音频链路（低延迟采集 + 流式播放 + 后台麦克风 + 前台服务类型 + 焦点/路由），不是 AI 部分。**

## 四、成本测算（BYOK，用户自付）

按「期末周 7 天 × 每天 20–30 分钟」测算：

| 方案 | 单价（每分钟） | 期末周合计 | 备注 |
|---|---|---|---|
| **管线式**（STT + 现有 DeepSeek + TTS） | ≈¥0.01/次 | **¥2–5** | 成本低一个数量级，且可继续用现有 Key |
| 通义 qwen3.5-omni-flash-realtime | ≈¥0.12 | ¥17–32（**有 100 万免费 token，约覆盖 8–14 小时纯音频 → 期末周很可能 ¥0**） | 国内直连 |
| 智谱 GLM-Realtime-Flash / Air | ¥0.18 / ¥0.30 | ¥25–38 / ¥42–63 | 国内直连 |
| 火山豆包端到端实时 | ≈¥0.5 | ¥70–100 | 价格取自转载来源，**未核实** |
| OpenAI gpt-realtime | ≈¥0.7–1.7 | **¥100–360** | 需代理 + 外卡 |

**结论**：BYOK 自付下「不限时」是现实的，但**只有 flash 轻量档能做到 ¥10/小时以内**。若选 OpenAI 或豆包高档位，「不限时」会变成用户的钱包风险。

**其他成本相关约束**：
- 端到端实时**静音也在计费**（音频按秒走），所以「常驻通话」是最贵的形态；按住说话只在说话时计费。
- 语音答复越长，输出音频 token 越贵 → 应「短答 + 屏幕卡片」，详解答复转文字。
- 厂商单会话上限（OpenAI 60 min / 通义 120 min）意味着「不限时」需要**到顶自动重连**才能兑现。

## 五、与品牌承诺的张力（必须处理）

本 App 的核心卖点是「本地优先 · 数据自有 · 隐私无忧」。语音功能意味着**麦克风与音频要发给第三方模型服务商**——这与品牌表述存在真实张力，必须主动化解，而不是回避：

- 按住才采集，**不做常驻热麦**
- **不保存录音**，只存本地转写文本（转写也仅存本地 SQLite）
- 明确提示「音频由你配置的服务商处理」，措辞与现有 AI 说明保持一致
- 权限默认关闭，由用户主动开启

> 这一点如果不能说清楚，语音功能对「隐私优先」的定位是负资产。

## 六、建议方案

### 第一期（MVP，建议先做）：语音作为「提问方式」，不做通话

- 在**现有 AI 追问页**加麦克风按钮：按住说话 → **转写显示在输入框、可编辑后再发送**
- 答案默认**文字**呈现（复用现有 `AiResponseWidget`），每条答案旁给一个「朗读」按钮
- 首页新增**「随手问名词」入口**（当前追问强绑定在题目上，`_currentAnalysis == null` 时会直接返回，无题上下文根本进不去——这是必须先补的入口）
- 转写与问答历史保存在本地，可回顾

**理由**：零新增依赖（用系统语音识别即可）、零新增 Key、把最大的社交成本与隐私问题一次性解决，同时立刻满足「随手问一句」的真实诉求。

### 第二期（可选）：「电话模式」

- 采用**管线式**（流式 STT → 现有 LLM → 流式 TTS）做「免手对话」，把成本压在 ¥0.01/次
- 若要做端到端实时体验，**默认接通义 qwen3.5-omni-flash-realtime**（国内直连 + 有免费额度），并明确告知用户这是另一个 Key
- 「不限时」的落地方式：不限累计时长 + 用户 Key 付费 + **界面实时显示本次消耗** + 静音超时自动挂断 + 到厂商单会话上限自动重连

### 明确不做

- 常驻通话（最贵、最不隐私、图书馆不可用）
- 唤醒词（误触高、耗电高、安静场所不可用）
- 后台/锁屏持续收听
- 自动朗读每一条回答（改为按需触发）

## 附：调研方法与不确定性

- 三路调研相互独立：①移动端音视频工程（读项目代码 + Android 平台约束）②LLM 应用架构与成本（查各家定价与文档）③产品与用户研究（场景拆解 + 竞品）。
- **已核实**：项目现状（权限/依赖/保活/AI 层）、Android 14+ 前台服务麦克风要求、OpenAI 与通义的会话上限与定价区间。
- **未核实**：豆包端到端实时的具体单价（来源为转载快照）、智谱的会话时长上限、各家在医学专业术语上的识别准确率（**无公开基准，三家均为宣传口径**）。若要选型，建议先做一次小样本实测：准备 30 个本专业名词（含 MHC、FSRS 这类缩写与「肝门静脉/肛门静脉」这类易混同音词），在三家各跑一遍看转写与回答质量。
